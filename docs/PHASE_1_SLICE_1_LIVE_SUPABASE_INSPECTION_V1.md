## Policies

### analyses SELECT policy

| Attribute | Value |
|-----------|-------|
| **Policy name** | Users can read own analyses |
| **Role** | `public` |
| **Command** | `SELECT` |
| **Condition** | `lower(user_email) = lower(auth.jwt() ->> 'email')` |

### Policy gaps and application pattern

- **No INSERT, UPDATE, or DELETE policies** were visible for `analyses`
- Current application uses **server-side service-role client** for writes (`app/api/scan/route.ts`) — service role **bypasses RLS**
- Current server components and server actions also use service-role for reads in production code paths

**Slice 1 planning implication:** New tables (`scan_records`, `consent_snapshots`) should likely **mirror this pattern**—server-side service-role writes for capture flow; user-owned SELECT policy keyed on `user_email` matched to `auth.jwt() ->> 'email'` if client-side or authenticated direct reads are introduced later. Exact policies deferred to SQL draft review.
